===============================================================================
🏗️ ARCHITECTURE DECISIONS
===============================================================================

WHY SEPARATE GAME TYPES?
✓ HTTP/API games: Stateless, simple debit→settle pattern
✓ Real-time games: Stateful, need fast cache access
✓ Keeps schema focused, queries performant

WHY CACHE FOR REAL-TIME?
✓ Live multiplier updates every 100ms
✓ Database can't handle that frequency
✓ Redis perfect for this (expires automatically)

WHY SERVER-SIDE PAYOUTS?
✓ Client can't be trusted with payout calculation
✓ Prevents fraud/manipulation
✓ Server validates based on seeds + result

SECURITY FEATURES:
✓ Atomic database transactions
✓ Wallet debit before game, credit after settlement
✓ Max 100x multiplier hard limit
✓ Provably fair (seeds for verification)
✓ Input validation on all endpoints
✓ 1% house edge built into multiplier calculations

📞 TROUBLESHOOTING
===============================================================================

"Class not found": Check you copied files to correct directories
"Table not found": Run php artisan migrate
"Cache driver error": Set CACHE_DRIVER in .env (redis, file, or array)
"Wallet not found": Ensure User→wallet relationship exists
"Seeds mismatch": Compare hash output with Flask game_engine.py
"Game timeout": Increase Cache TTL or add retry logic
